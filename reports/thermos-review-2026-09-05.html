P1B01 · defect

Retained dev versions block promotion and crash quarantine

src/lib/server/releases.ts:1076–1079
src/lib/server/releases.ts:1263–1266

Promoting the newest binary fails when an older dev version of the same package and architecture exists. Crash quarantine also fails when a stable package already has a dev version. The transaction rolls back; a crash-affected package remains stable.

Why it happens
The snapshot calculation removes all matching package versions, and the database assertion subtracts the same count. The transaction only changes the selected release, so retained dev history makes expected and actual counts differ.
Smallest useful fix
Compute the final release rows and repository index separately. Preserve historical releases, calculate assertions from the rows actually moved, and build the snapshot from the resulting channel state. Keep the atomic assertions.
Regression check
Promote the latest of two dev versions; quarantine a stable version while another dev version exists. Assert channel history and the actual signed database contents.
Evidence · Reproduced · SQLite + in-memory R2 + signer stub

Two production-function probes reproduced CHECK constraint failed: expected=actual: dev foo 1.0 + dev foo 2.0 → promote 2.0; stable foo 1.0 + dev foo 2.0 → quarantine 1.0. Both leave the original channels intact. Existing tests explicitly retain multiple dev versions, so this is supported state.

P1B02 · defect

A transient signer failure permanently blocks rollback retries

src/lib/server/releases.ts:1148
src/lib/server/releases.ts:1157–1161

A signer outage during rollback leaves the release stable. Retrying after the service recovers fails on an immutable-object digest mismatch, requiring storage intervention to complete the rollback.

Why it happens
Rollback writes a manifest containing issuedAt to a fixed key derived from the target release before signing the repository or committing channel changes. The next attempt generates different bytes for that same immutable key.
Smallest useful fix
Use an immutable manifest key per rollback operation or content digest, and activate it through release_rollbacks in the successful transaction. Reuse a persisted operation on retries where appropriate; do not weaken immutable-object checks.
Regression check
Fail signing after manifest creation, advance time, then retry successfully with the same inputs. Also test a transaction failure after signing.
Evidence · Reproduced · controlled clock + production rollback function

With a signer returning 503, the first attempt failed after writing the manifest. Advancing the clock by two seconds and restoring the signer made the same rollback fail with 'does not match expected digest'. The release remained stable.

transient signer failure poisons subsequent rollback

P2B03 · defect

Recipe upgrades leave two stable versions and no rollback target

src/lib/server/releases.ts:911–913
src/lib/server/releases.ts:1025–1032

Promoting a Surface B recipe update leaves the previous recipe marked stable and records no previous_release_id. Rolling back the new recipe then fails with 'No compatible previous release is available for downgrade.'

Why it happens
The previous-release lookup uses currentStable(), which loads binary releases only. Repository membership and release lifecycle are conflated, so recipe-only predecessors are invisible to the channel transition.
Smallest useful fix
Look up the current stable predecessor across both surfaces for channel changes and rollback history. Filter to binary packages only when constructing the pacman repository database.
Regression check
Promote recipe 1 → recipe 2, verify recipe 1 becomes withdrawn and recipe 2 references it, then roll back. Include a surface-change case.
Evidence · Reproduced · real Ed25519 attestation + SQLite

A probe with a real Ed25519-signed recipe attestation promoted foo 2.0 over stable foo 1.0. It observed two stable rows, a null predecessor on 2.0, and a rejected rollback.

recipe upgrade leaves old stable release and loses rollback target

P2B04 · defect

Recipe rollback verifies the wrong PKGBUILD digest

src/lib/server/releases.ts:626–638
src/lib/server/releases.ts:1155

For a Surface B release with separate internal and public recipes, the rollback client downloads the public PKGBUILD and rejects it at sha256sum. The advertised downgrade cannot run.

Why it happens
Publication stores public_recipe when available. Rollback's query loads recipe_sha256 and places that internal-build hash in the manifest instead of the digest of the published recipe bytes.
Smallest useful fix
Carry the published recipe identity into rollback. Use public_recipe_sha256 for recipe releases when present, or verify/hash the immutable object referenced by recipe_key.
Regression check
After fixing predecessor selection (B03), roll back a recipe release whose public_recipe differs from recipe and verify the downloaded object against the manifest.
Evidence · Reproduced · production manifest generation + exact object hash

A probe stored a public recipe using a vendor URL and a different internal recipe using sealed storage. rollbackRelease emitted the internal hash; hashing the object at the manifest's recipe URL produced a different digest.

Surface B rollback advertises internal recipe hash

P2B05 · defect

Crash reports arriving during signing bypass the promotion gate

src/lib/server/releases.ts:985–986
src/lib/server/releases.ts:1031–1033

A release can become stable with an unresolved crash report even though promotion policy requires zero unresolved reports. Signing introduces a window between the eligibility check and the final transaction.

Why it happens
The initial crash-count check runs before asynchronous snapshot creation and signing. The UPDATE that promotes the release checks only channel='dev'; the atomic batch does not recheck the crash gate.
Smallest useful fix
Repeat mutable eligibility predicates in the final transaction, including the unresolved-crash check, and assert that each candidate transition succeeded. Retain the initial check for a useful early error.
Regression check
Insert a crash during the signing await and expect promotion to abort atomically, keeping the release in dev.
Evidence · Reproduced · controlled asynchronous interleaving

A signer stub inserted an unresolved crash report after the initial check but before returning the signature. promoteBatch completed successfully and left that release stable with one unresolved report.

crash arriving during signing does not block promotion

P2B06 · defect

Nonlocal HTTP endpoints can receive signing credentials

scripts/deploy.ts:56–64
scripts/deploy.ts:139–147
signer/src/index.ts:129–146
signer/src/index.ts:179–183
signer/src/index.ts:293–298

If a nonlocal http:// origin is configured, signing-control or KMS bearer credentials are sent without transport encryption and can be captured by an observer on that network path. This is a conditional configuration weakness; the review did not establish that any deployed endpoint currently uses HTTP.

Why it happens
Production URL validation accepts HTTP and copies PUBLIC_ORIGIN into CONTROL_ORIGIN. The signer accepts both HTTP and HTTPS for control and KMS URLs, then attaches its bearer credentials. Redirect rejection does not protect the initial plaintext request.
Smallest useful fix
Require HTTPS for nonlocal control and KMS endpoints, and require HTTPS in production config generation. Keep any needed HTTP exception explicit and limited to loopback development; never silently treat arbitrary HTTP hosts as local.
Regression check
Reject nonlocal HTTP before fetch; verify that HTTPS still works and only explicitly supported loopback development origins can use HTTP.
Evidence · Reproduced · mocked signer fetch; deployment/control path traced

A production signer probe configured KMS_SIGNER_URL=http://kms.example and intercepted fetch locally. It observed http://kms.example/v1/public-key with Authorization: Bearer dummy-kms-credential. No network request was sent. The corresponding control-token path was traced in source.

nonlocal HTTP KMS endpoint receives bearer credentials

class MemoryR2 {
  readonly objects = new Map<string, Uint8Array>();
  private object(key: string) {
    const bytes = this.objects.get(key);
    if (!bytes) return null;
    return { size: bytes.byteLength, etag: key, httpEtag: `"${key}"`, customMetadata: key.startsWith('signatures/') ? { signatureSha256: 'a'.repeat(64) } : {}, httpMetadata: {}, body: new Response(bytes.buffer as ArrayBuffer).body, arrayBuffer: async () => bytes.slice().buffer as ArrayBuffer, text: async () => new TextDecoder().decode(bytes) };
  }
  head(key: string) { return Promise.resolve(this.object(key)); }
  async get(key: string, options?: R2GetOptions) {
    const conditional = options?.onlyIf;
    const etag = conditional && 'etagMatches' in conditional ? conditional.etagMatches : undefined;
    if (typeof etag === 'string' && (etag.startsWith('"') || etag.endsWith('"'))) {
      throw new Error(`Conditional ETag should not be wrapped in quotes (${etag}).`);
    }
    if (typeof etag === 'string' && etag !== key) return null;
    return this.object(key);
  }
  async put(key: string, value: ArrayBuffer | ArrayBufferView | ReadableStream<Uint8Array>, options?: R2PutOptions) {
    const bytes = value instanceof ReadableStream
      ? new Uint8Array(await new Response(value).arrayBuffer())
      : value instanceof ArrayBuffer ? new Uint8Array(value) : new Uint8Array(value.buffer as ArrayBuffer, value.byteOffset, value.byteLength);
    if (typeof options?.sha256 === 'string' && await sha256(bytes) !== options.sha256) throw new Error('checksum mismatch');
    this.objects.set(key, new Uint8Array(bytes));
    return this.object(key);
  }
}

function base64(bytes: ArrayBuffer): string {
  let binary = '';
  for (const byte of new Uint8Array(bytes)) binary += String.fromCharCode(byte);
  return btoa(binary);
}
